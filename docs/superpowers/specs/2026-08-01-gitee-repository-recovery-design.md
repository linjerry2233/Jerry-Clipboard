# Gitee 云同步仓库重建与云端数据删除设计

## 背景与根因

Windows 客户端当前无法同步，Gitee 返回：

```text
Repo size: 1085.527MB, exceeds quota 1024MB
Push rejected for repository [size exceeds limit]
```

这不是分支冲突或 SSH 认证失败。当前仓库已经超过 Gitee 社区版容量限制，服务端会拒绝普通 push、删除数据后的 commit push，以及用于重写历史的强制 push。

代码侧还存在长期膨胀原因：全量同步会用随机 nonce 重新加密每一条本地数据。相同明文每次会产生不同密文，导致 Git 为未变化数据持续保存新 blob。

## 目标

1. 删除并重新创建 `linjerry666/jerry-suit-sync`，恢复 Windows 和 Android 的云同步能力。
2. 重建后只上传当前有效数据快照，不恢复旧提交历史。
3. 修复设置中的“清理云端文件”和“彻底清空云端及历史”。
4. 防止全量同步重复改写未变化的密文文件。
5. 将 Gitee 的真实错误显示给用户，不再统一显示“远端有冲突或网络错误”。

## 不可逆边界

仓库删除后，Gitee 上的以下内容会被永久移除：

- 当前分支及所有历史 commit；
- 仓库设置、WebHook、部署密钥等仓库级配置；
- 仅存在于该仓库的问题、PR 或附件（如果存在）。

以下本地内容必须保留：

- Jerry Suite 本地数据库；
- AES 密钥；
- SSH 私钥和公钥；
- 当前云同步配置中除仓库初始化状态外的用户设置。

不额外保留旧云端 Git 历史备份，以满足彻底移除旧历史的目的。

## 仓库恢复流程

1. 停止正在运行的 Jerry Suite，避免重建期间后台同步写入仓库。
2. 记录现有远端地址、目标分支和仓库可见性。
3. 在 Gitee 删除 `linjerry666/jerry-suit-sync`。
4. 使用相同命名空间、仓库名和可见性重新创建空仓库，默认分支为 `main`。
5. 保留现有 SSH 密钥；若 Gitee 的仓库级部署密钥随删除丢失，则重新配置公钥。账号级 SSH 公钥不需要重配。
6. 重置应用本地 `cloud_sync_repo` 的 Git 历史，但保留应用数据库和密钥。
7. 从本地数据库生成一次当前快照，创建新的根 commit 并推送。
8. 复验远端 HEAD、文件树和应用拉取/推送状态。

## 应用修复设计

### 图片同步默认策略

设置页保留“同步剪贴板图片”开关，但默认策略改为关闭：

1. 新安装创建 `CloudSyncConfig` 时，`syncClipboardImages` 默认为 `false`；
2. 读取没有该字段的旧配置时按 `false` 处理；
3. 配置中已经明确保存 `true` 或 `false` 时保留该值，不在升级时强制覆盖；
4. 本次恢复使用的 Windows 配置明确写入 `false`，确保首次重建快照只包含文本和链接；
5. Windows Git、Android REST、Android SSH、增量同步和全量同步继续读取同一个配置字段；
6. 关闭开关只影响云同步，不删除本地剪贴板图片。

重建云端快照时，云端当前分支不得包含 `isImage == true` 的剪贴板条目。用户以后主动开启开关后，新发生或被全量同步选中的图片才允许上传。

### 避免重复密文

全量同步处理每个已有云端文件时：

1. 读取现有加密 envelope；
2. 使用当前 AES 密钥解密；
3. 将现有明文与当前序列化明文比较；
4. 完全相同时保留原文件，不重新加密、不写磁盘；
5. 内容变化、文件不存在、旧文件无法解密或算法不匹配时，才生成新密文。

这样不改变随机 nonce 的安全属性，也不会为了去重改成确定性加密。

### 保留真实 Git 错误

Git 网络操作失败时记录最近一次命令的精简 stderr。同步、按类型清理、全部清理应返回真实原因，例如：

- 仓库超过容量配额；
- 分支受保护，拒绝强推；
- SSH 认证失败；
- DNS 或连接超时；
- 非快进推送。

不得在界面中暴露 token、私钥路径内容或完整带凭据 URL。

### “清理云端文件”

该按钮保留仓库历史，只删除目标分支当前文件：

1. fetch 并切换到远端最新 HEAD；
2. 删除所有受管数据目录中的 JSON 文件；
3. commit 并 push；
4. fetch 后复验远端数据文件数量为零；
5. 成功后暂停自动同步，防止本地数据立即重新上传。

如果仓库已经超额并被 Gitee 拒绝 push，界面明确提示需要使用“彻底重建云端仓库”，不能报告清理成功。

### “彻底清空云端及历史”

普通情况下继续采用空 tree、无 parent 根 commit、强制更新分支并复验的实现。

如果服务端因为仓库容量超额而拒绝任何 push，应用显示平台限制和恢复建议。仅凭 SSH Git 协议不能安全地自动删除并重建 Gitee 仓库；自动重建需要额外的 Gitee API 凭据，因此不把账号级仓库删除能力隐式放入普通清理按钮。

设置页把“删除当前文件”和“改写提交历史”保持为两个独立按钮，继续使用二次确认；彻底清理不自动删除整个 Gitee 仓库。

## 测试设计

新增或扩展本地 bare Git 集成测试：

1. 两次全量同步相同业务数据时，第二次不产生工作区变化和新 commit；
2. 单条业务数据变化时，只改写对应文件；
3. Git push 返回容量超额 stderr 时，`SyncResult.message` 包含容量原因而非兜底冲突文案；
4. 清理当前文件后，远端受管 JSON 文件为零；
5. 彻底清理后，远端只有一个空根 commit；
6. 清理成功后自动同步保持暂停。
7. 新配置和缺失字段的旧配置均默认关闭图片同步；显式 `true` 能正确持久化并恢复。
8. 图片同步关闭时，Windows Git、Android REST、Android SSH 和增量事件均跳过图片条目，但文本条目正常同步。

## 验收标准

- 新建仓库的首次快照 push 成功；
- Windows 客户端同步成功，远端 HEAD 与本地 HEAD 一致；
- Android 客户端能从新仓库拉取当前快照；
- 连续两次全量同步且本地无变化时，第二次不创建 commit；
- 新安装及缺失字段配置默认只同步文本和链接；
- 当前 Windows 配置为 `syncClipboardImages: false`；
- 设置页两个清理按钮均返回可验证结果；
- Gitee 拒绝时显示真实、脱敏的服务端原因；
- `flutter analyze`、完整 `flutter test`、Windows Release 构建通过。
