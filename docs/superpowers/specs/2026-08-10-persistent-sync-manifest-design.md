# 持久化变更清单与删除墓碑同步设计

## 背景与目标

当前双向同步在拉取后仍会遍历并上传本地全部数据。REST 后端会为每条记录重新加密并 PUT，SSH 后端会重新构建加密 blob；即使仓库小于 1 MB，也会产生明显的重复流量和 CPU 开销。

本设计同时解决以下问题：

1. 每条记录使用稳定的 `syncId`，本地修改只更新对应云端文件。
2. 未变化数据不再重复上传，拉取后不再被立即重新上传。
3. 跨设备删除可靠传播，并保留 30 天删除墓碑。
4. 云端写入完成后只触发一次本地数据刷新。
5. Android 待办仅允许右滑完成，不允许左滑删除。
6. Android 同步提示显示在底部导航操作区上方。
7. 自动同步只在本地发生变化时立即增量推送，定时任务只轮询云端同步索引。

## 方案选择

### 方案 A：持久化变更清单 + 删除墓碑清单（采用）

本地持久化每个 `dataType/syncId` 的明文摘要。同步时先序列化明文并计算 SHA-256；摘要没有变化就跳过加密和上传，摘要变化才更新原文件。删除操作记录到本地删除清单，并向云端写入加密墓碑和删除清单。

优点是不会为比较内容下载全部云端文件，兼容现有文件路径，且能覆盖应用重启、离线删除和换机恢复。缺点是需要维护本地状态文件和云端删除清单的一致性，因此所有写入都必须采用原子保存和合并策略。

### 方案 B：每次下载所有远端文件后比较明文

实现简单，但会把当前重复上传问题变成重复下载问题，无法满足低流量目标，不采用。

### 方案 C：只依赖 commit/文件 SHA

改动较少，但无法识别本地删除、应用重装后状态缺失和部分记录修改，不足以保证跨设备删除和恢复，不采用。

## 数据模型与持久化

新增 `SyncStateStore`，文件位于应用支持目录 `cloud_sync_state.json`，采用临时文件写入后原子替换。

```json
{
  "version": 1,
  "entries": {
    "todo/<syncId>": {
      "digest": "sha256-of-serialized-plaintext",
      "syncedAt": "2026-08-10T00:00:00Z"
    }
  },
  "deleted": [
    {
      "dataType": "todo",
      "fileName": "todo/<syncId>.json",
      "deletedAt": "2026-08-10T00:00:00Z",
      "source": "local",
      "uploadedAt": null
    }
  ]
}
```

`fileName` 是云端文件名对应的删除 ID；数据类型单独保存，避免不同目录下同名 ID 冲突。`source` 用于诊断，不参与冲突判断。记录进入清单后，即使本地数据已经物理删除，也可以在下次启动或同步时继续推送墓碑。

云端新增加密文件 `meta/sync_index.json`，固定 `dataType=sync_index`、`syncId=sync_index`。该文件是轻量轮询入口，记录当前已保存的云端文件 ID、明文摘要和更新时间，并记录 30 天内的删除 ID：

```json
{
  "version": 1,
  "generation": "uuid",
  "updatedAt": "2026-08-10T00:00:00Z",
  "entries": {
    "todo/<syncId>.json": {
      "digest": "sha256-of-serialized-plaintext",
      "updatedAt": "2026-08-10T00:00:00Z"
    }
  },
  "deleted": [
    {
      "fileName": "todo/<syncId>.json",
      "deletedAt": "2026-08-10T00:00:00Z"
    }
  ]
}
```

索引本身加密保存；ID 是云端文件名，`digest` 用于校验“索引记录”和“实际文件内容”一致。云端删除时保留现有 `<dataType>/<syncId>.json` 加密墓碑以兼容旧版本，同时更新索引中的 `deleted` 列表。云端墓碑和索引删除项保留 30 天，超过 30 天才允许清理。

## 同步流程

### 本地变更即时同步

1. 本地数据库产生 create/update/delete 事件时，增量同步服务立即排队执行，不等待固定轮询间隔；同一事件循环内的重复事件合并为一个 `dataType/syncId` 操作。
2. create/update 计算序列化明文摘要。摘要变化才加密并更新同一个云端文件；摘要不变不产生网络写入。
3. delete 先写入本地删除清单，再写入同一文件路径的墓碑，并更新云端同步索引。
4. 数据文件和墓碑成功写入后才更新本地摘要/删除记录的 `uploadedAt`；失败时保留待处理状态，下一次本地事件或轮询继续重试。

### 定时云端轮询

1. 自动同步配置的前台 Timer 和 Android WorkManager 只请求 `meta/sync_index.json`，不执行全量 `_pushAll`，也不下载各数据文件。
2. 若索引 `generation`/摘要未变化，直接返回“无远端变化”，不产生数据流量。
3. 若索引变化，按索引的新增/修改 ID 下载对应文件，按 `deleted` ID 删除本地数据；实际文件解密后必须匹配索引摘要，否则本次轮询失败并保留旧索引游标。
4. 远端变更处理完成后再检查本地待处理变更，必要时只推送本地变化 ID；所有入口继续由 `CloudSyncCoordinator` 串行化。
5. 没有索引的旧仓库只在首次迁移时遍历现有目录并建立索引，完成后后续轮询只读取索引。

### 双向同步

1. 同步开始前运行本地删除清单维护：重新确认被标记 ID 的本地数据已删除，清理超过 30 天的本地清单记录。
2. 拉取远端 HEAD/index 游标；索引未变化时不下载数据。
3. 若远端包含删除索引，先合并清单并删除对应本地数据；云端来源的删除不会进入本地上传队列。
4. 处理索引列出的新增/修改文件。成功解密并落库后保存该文件的明文摘要；墓碑文件会删除本地对象并更新删除清单。
5. 推送本地数据：序列化并计算摘要，只对新增或摘要变化的 `syncId` 加密并更新原路径文件。
6. 数据文件写入成功后，读取并合并云端 `meta/sync_index.json`，最后写索引；索引写入失败时保留本地待处理状态，不能报告完整同步成功。
7. 清理云端超过 30 天的墓碑文件和索引删除项。
8. 所有数据库写入结束后发出一次 `cloudDataChanged`，Provider 从 Isar 重新读取并显示。

### 后端差异

- REST：摘要相同就不执行 PUT；变化时仍使用同一 `<dataType>/<syncId>.json` 路径并携带现有 SHA，确保是更新而不是新增重复文件。索引最后写入，若索引写入失败下一次轮询会重试校正。
- Windows Git CLI：继续使用 `EncryptedSyncFileWriter` 的明文比较，并将删除清单纳入同一 Git 提交；未变化文件不改写。
- SSH Git：在同一 commit 中提交数据文件、墓碑和同步索引；构建 tree 时复用状态清单中已知的 blob SHA 和远端对象，只有摘要变化才生成新的加密 blob，避免随机 IV 导致每次 pack 都变化。

## 删除语义

- 本地删除事件先写入删除清单，再由增量同步服务推送墓碑；没有 `syncId` 的本地新增数据无需写入云端删除记录。
- 远端删除清单或墓碑到达后，按 `dataType + syncId` 删除本地记录，并写入本地清单，防止旧查询或后续同步把数据重新显示。
- 本地每天至少执行一次清单维护；清理操作幂等，不会因为对象已不存在而失败。
- 删除墓碑保留 30 天，之后才从云端文件和清单中清除。30 天是跨设备离线恢复删除消息的最大窗口。
- 清空云端、清空云端历史或切换仓库时，删除清单与同步摘要一起重置，避免旧仓库的墓碑作用于新仓库。

## 自动同步状态机

- `localChange`：本地记录发生变化，立即进入 `pushDirtyIds`，只处理受影响的 ID。
- `remotePoll`：达到用户配置的间隔后，只读取同步索引；索引无变化则结束。
- `remoteChanged`：索引变化后进入 `pullIndexedIds`，完成摘要校验和删除应用后刷新 UI。
- `reconcile`：索引缺失、摘要不匹配或写索引失败时进入一次完整目录校正，并返回可重试错误；不会把不一致状态标记为成功。

## UI 行为

- Android 待办 `Dismissible.direction` 固定为 `DismissDirection.startToEnd`；右滑只调用完成/取消完成，返回 `false` 保留卡片。删除只能从长按菜单或显式删除按钮执行。
- 同步增量提示和删除成功提示使用统一的底部偏移：Android 为系统安全区加底部导航栏高度，Windows 保持原有窗口底部间距，确保提示不遮挡功能按钮。
- 同步结束事件只触发一次；刷新期间的旧异步查询不能覆盖新快照。

## 错误与恢复

- 清单文件损坏时备份损坏文件并从空状态恢复，但当前同步必须报告需要重新校验，不得静默覆盖云端。
- 摘要更新只在对应云端写入成功后提交；上传失败保留待上传状态，下一次同步重试。
- 云端删除清单更新遇到 SHA 冲突时重新读取、合并并最多重试有限次数；重试失败返回同步失败，不显示成功。
- 拉取阶段任一文件解密/解析失败时不推进远端游标，下一次继续重试。

## 测试策略

- `SyncStateStore` 单元测试：摘要保存、原子恢复、旧版本兼容、30 天删除清理、重复删除幂等。
- 删除清单测试：本地/远端合并取较新时间、墓碑应用后本地数据消失、云端清单过期项清理。
- 同步索引测试：索引 ID/摘要与实际文件校验、generation 未变化时零数据下载、索引新增/删除触发精确增量拉取。
- REST/SSH 推送测试：新增记录创建一次文件、相同摘要不产生 PUT/blob、修改同一 `syncId` 只更新原文件、上传失败不更新摘要。
- 自动同步测试：本地事件立即触发增量推送，轮询只读取索引，轮询无变化不调用数据拉取。
- 刷新测试：一次完整云端批次只触发一次 `cloudDataChanged`，拉取后所有 Provider 重新读取。
- Android UI 测试：待办只存在右滑方向，左滑不触发删除；同步提示底部位置高于导航栏。
- 完成后运行 `flutter analyze` 和全量 `flutter test`，并构建签名 Android Release APK；真机安装后验证同步、修改、跨设备删除和提示位置。
