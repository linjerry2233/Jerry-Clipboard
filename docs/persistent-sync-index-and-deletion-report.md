# 持久化同步索引与删除同步修复报告

## 范围

本次修复覆盖 Windows 与 Android 共用的 REST、Git CLI、SSH Git 三套云同步实现，目标是消除“仓库不足 1 MB 但每次同步产生大量流量”“拉取 0 条”“同步后业务数据短暂出现又消失”以及跨设备删除不能传播的问题，同时调整 Android 待办手势和同步提示位置。

## 根本原因

1. 常规同步在拉取后仍执行全量推送。REST 会逐条重新加密并 PUT；SSH Git 因随机 IV 每次都会生成不同 blob，即使明文没有变化也会重新上传。
2. 同步状态主要依赖 commit/HEAD 游标，无法准确表达单条记录的新增、修改、删除以及本地状态丢失；远端 HEAD 未变化时可能错误返回“0 条”。
3. 删除只存在于瞬时事件或单个墓碑文件中，缺少可持久化、可合并、可过期的删除清单，离线设备无法可靠获知另一台设备的删除。
4. 定时自动同步调用完整双向同步，导致无本地变化时仍产生业务数据请求；本地变化又需要等待固定防抖时间。
5. 云端写入分多个阶段通知 UI，异步查询可能乱序完成，旧查询结果会覆盖拉取后的新快照。

## 采用的架构（方案 A）

- 每条业务记录继续使用稳定 `syncId`，云端路径固定为 `<dataType>/<syncId>.json`；修改记录只更新原路径。
- 本地 `cloud_sync_state.json` 保存 `dataType/syncId` 对应的 SHA-256 明文摘要、最近同步时间和删除记录。
- 云端新增加密索引 `meta/sync_index.json`，保存活动文件 ID、摘要、更新时间、generation，以及 30 天内的删除项。
- 数据文件或墓碑先写，索引最后写；远端写入失败时不推进本地摘要或游标，后续可安全重试。
- 本地 create/update/delete 事件在当前事件循环内合并后立即增量推送；定时器和 Android WorkManager 只轮询轻量索引。
- 摘要没有变化时跳过重新加密和上传；SSH Git 尽量复用已有 blob，避免随机 IV 导致无意义的新对象。
- 拉取按照索引差异只下载新增或摘要变化的 ID，并校验解密后的明文摘要；校验失败则整次失败且保留旧游标。

## 删除传播与 30 天策略

- 本地删除先持久化到删除清单，再上传同一路径墓碑并合并进云端索引。
- 另一台设备轮询到删除项后，按 `dataType + syncId` 幂等删除本地记录；云端写入期间抑制反向增量事件，避免删除回环。
- 墓碑和索引删除项保留 30 天，为离线设备提供恢复窗口。
- 只有已被远端确认、且超过 30 天的删除项才允许清理；未上传或近期记录不会被提前移除。
- 启动和定时轮询路径执行本地删除状态维护；重复运行不会报错，也不会恢复已删除数据。

## UI 与显示稳定性

- 一次云端拉取由统一数据库批次包围，全部写入完成后只发送一次 `cloudDataChanged`。
- Provider 使用刷新代次保护；分页加载和按需图片读取继续保留，旧异步结果不能覆盖新快照。
- Android 待办只允许从左向右滑动切换完成状态，取消从右向左直接删除；删除仍可通过显式入口完成。
- Android 同步/删除提示位于底部导航栏和安全区上方，Windows 保持原桌面间距。

## 流量测量方法

建议在同一数据集下分别记录三种场景的网络字节数与请求路径：

1. 无本地、无远端变化：应只读取 `meta/sync_index.json`，业务文件上传和下载均为 0。
2. 修改一条记录：应更新同一个 `<dataType>/<syncId>.json`，并写一次索引；不应访问其他业务文件。
3. 远端新增或删除一条记录：应读取索引和对应单个业务文件/墓碑，不应全量重建仓库。

## 资源与极端情况兜底

- 摘要比较发生在加密前，未变数据不重新生成密文，可降低 CPU、内存分配和网络流量。
- 列表继续分页，剪贴板图片按需读取；默认不同步图片时不会为同步扫描加载图片大字段。
- 所有云操作由协调器串行化，避免手动同步、即时推送和后台轮询并发争用数据库或远端 SHA。
- 索引缺失时执行一次迁移/校正；索引损坏、摘要不一致、远端冲突或写入失败时明确返回失败，不把部分结果标记成成功。
- 本地状态采用临时文件后原子替换；异常中断后保留可恢复状态。回滚时可以删除本地同步状态文件并执行一次显式拉取重建，但不得删除本地业务数据库或签名密钥。
